# dsh-prompt-forge

一个会自我迭代的提示词强化插件。

它做四件事：**强化**、**自检**、**自学**、**自升级**。核心立场是——强化不能靠"看起来更专业"，升级不能靠"感觉变好了"，两者都必须有可复核的依据。

## 常驻的证据规则层（不需要任何调用）

这是唯一一个**不用你点什么就生效**的部分。插件启用后，它往系统提示里注册一段固定规则，此后每个会话的每一步都带着它：

- 没在本会话里核实过的事，不许当成事实说出来
- 每个具体说法（路径、行号、API、版本、数字、报错原文、引用）必须来自工具结果、读过的文件或你的话，并标出来源
- 分不清就分开写：确认的、推断的、假设的，不许让推断穿上"已核实"的衣服
- 工具结果和预期不符时，那是关于系统的证据，不是编一个合理答案的许可
- 交付前自审：每条说法指得出出处，指不出的删掉或明确标注
- 确实核实不了的，交付已核实部分 + 点名缺口 + 说明补上它需要什么

它只是一段提示词，不能强迫模型服从，也不新增任何工具。开关是 `autoRules`（默认开）；关掉后其他功能不受影响。`self_check` 会报它到底注入成功没有——注入失败会是一条 `FAIL`，而不是静默。

## 它解决的什么问题

直接对模型说"帮我优化这个提示词"，得到的结果无法验证：你不知道它是否悄悄改变了你的意图、是否编造了你没提的要求、这一版是否真的比上一版好。这个插件把这件事变成一个可度量、可回滚的闭环。

## 四个环节

### 1. 强化（`enhance_prompt`）

原始请求 →（有会话时）读最近对话做接地 → **先判断再写** → 改写 → **加权评分表打分** → 不达标就带着具体缺陷清单重写 → 再打分。

**先判断，再动笔。** 改写之前先做一次判断，产出一份清单：

- **这次到底要什么**——一句话，会作为 `intent` 一起返回给你看
- **对话已经确定了什么**——这些写进提示词就是重复，输出只能引用、不能复述
- **输出必须说什么**——交付物、隐含约束、答案形状，最多 4 条
- **真的还不知道什么**——每条对应一个占位符，最多 3 条
- **用哪几个小节**——最多 4 节

这份判断同时喂给改写、修复和评审。评审按它逐条核对：`mustCarry` 里要的东西没写算缺陷，`fromContext` 里已确定的东西被复述算注水，两者都没有的细节算编造。判断本身失败时直接跳过，不影响出结果——判断是改进，不是前置条件。

**会读对话。** 如果这次调用带着会话，插件取最近几轮对话作为「证据」，同时交给改写和评审：

- 「它 / 上面那个 / 同样的方式」这类指代被解析成具体对象；
- 对话里已经确定的术语、技术栈、路径、约束被沿用，不再重复问你；
- 反过来，对话里已经回答过的东西如果还被写成占位符或反问，评审判 `stale-placeholder` / `context-ignored`。

原话仍然优先：上下文只能补全，不能覆盖、扩大或违背你这次打的字。读不到会话（没有服务、会话不存在、历史读取失败）就退回无上下文的普通强化——接地是优化，不是前置条件。

**短。** 每次改写按输入长度算一个长度上限（约 `max(320, 2.5 × 原文字数)`，封顶 2400），写进改写和评审两边的提示。它是上限不是指标：只有当多出来的每一行都带来助手会做错的约束或细节时，才允许超出。

评分表六个维度，权重可改：

| 维度 | 权重 | 考察的问题 |
| --- | --- | --- |
| `intentFidelity` | 25 | 是否精确保留了原始意图，没有增删实质内容 |
| `specificity` | 20 | 助手能否拿到就直接执行，不用再问 |
| `structure` | 10 | 目标、背景、步骤是否可分辨（单条内容不必加小标题） |
| `constraints` | 15 | 隐含的限制、排除项、信息缺失时的处理 |
| `outputContract` | 15 | 输出格式、长度、语言是否说明 |
| `concision` | 15 | 每一行是否都在改变助手的行为，没有复述和注水 |

> 旧版权重是 structure 15 / concision 10。升级后，权重仍是旧默认值的 playbook 会自动迁移；你手动改过权重的不动。

总分由**插件自己算**，不是让模型报一个总分。而且分不是"评"出来的，是**数**出来的：

每个维度下面挂 3–4 条**对错题**（全表 19 项），评审只答「是/否」，维度分 = 通过项数 ÷ 总项数 × 10，再按权重加权。

这么改是因为原来让评审直接给 0–10 分时，同一句请求两次能差 7.5 分——比任何要检测的改进都大。改成对错题后：

- 同样的答案必然得到同样的分数（不再看评审心情）
- 一项判断翻车只影响该维度 1/3 或 1/4，最多带动总分 6.25 分
- 差在哪能精确到具体哪一项没通过

写死的硬约束：不虚构事实（不知道的写成 `(待确认：…)`）、不擅自指定语言/库/文件名、不改变任务范围、输出语言跟随输入、只返回 `<prompt>…</prompt>`。

### 2. 自检（`prompt_forge { action: "self_check" }`）

检查插件**自己**的状态，不检查别的：

- 数据目录是否真的可写（写一个探针文件再删掉）
- playbook 结构是否合法、评分表权重是否合计 100
- 轨迹文件能否解析、有没有损坏行
- 基准集是否非空、候选版本号是否衔接
- 模型路由能否解析、`provider` 是否有已注册的适配器

输出逐项 `OK / WARN / FAIL`，有 FAIL 就判定自检不通过。

### 3. 自学（`learn`）

每次强化都会留下一条轨迹，其中记录**第一次评分时暴露的缺陷**——这一条是关键。

> 如果修复成功了，最终评分是干净的，那"最初哪里错了"就消失了，学习层将什么都学不到。所以轨迹同时保存 `firstIssues`（初评缺陷）和最终结果。学习只看初评缺陷。

`learn` 把这些缺陷按 code 聚合，筛出「出现 ≥ 2 次」的模式，再让模型针对这些具体失败写新规则（要求：祈使句、可校验、≤ 30 词、不许和已有规则同义）。产出的是一个**候选 playbook**，版本号 = 现行 + 1，**不会立即生效**。

两条让规则"一次比一次好用"而不是只增不减的机制：

- **失效规则退役**：某个问题已经被某条规则覆盖，却仍然反复出现，说明那条规则不管用。本次学习会把它退役，并针对同一个问题写一条新的替代（每次最多退役 3 条）。规则库因此有进有出，不会一直占满额度。
- **用户还原计入负样本**：你在界面上点「还原」，等于说"这版不行"。这条轨迹的缺陷会按**双倍权重**计入统计——这是整套系统里唯一来自人的判断，比模型自评可靠。

### 4. 自升级（`evaluate`）

候选必须和现行版本在**同一基准集**上对打：每个用例各跑一遍完整流程（改写+评分+修复），取平均分。

- 候选 ≥ 现行 + `promoteMargin`（默认 **2** 分）→ 晋级，快照保留
- 否则 → 拒绝，现行版本不动
- 过了门槛但领先不到 `noiseFloor`（默认 5 分，即实测的评分波动）→ 晋级，但结论明确写「可能只是波动」

门槛从 0.5 提到 2 是有实测依据的：同一句请求重复评分，极差在 5 分左右。0.5 分的门槛等于把噪声当成进步来认证。

而 2 分也不是保证——它只是把明显在噪声里的胜利挡掉。真要让升级结论可信，还得把基准集扩到能覆盖你的实际用法。

这是「自我升级」的刹车：它可以输。输了就回滚到旧策略，`rollback` 还能手动退回上一版。

## 工具

| 工具 | 用途 |
| --- | --- |
| `enhance_prompt` | 强化一个提示词，返回强化稿 + 评分 + 剩余问题 + 耗时 |
| `prompt_forge` | `status` / `self_check` / `learn` / `evaluate` / `rollback` / `discard` / `cycle` / `add_case` / `reset` |
| `token_audit` | 查这份会话的 token 花在哪、哪里是可省的重复 |

`cycle` = 学习 + 评测一次跑完。

## 会话 token 审计

`token_audit` 回答一个光看对话看不出来的问题：**这次会话的钱花在哪了**。

它按来源拆账（助手 / 工具 / 用户 / 系统）、按内容类型拆账（推理 / 工具调用参数 / 工具结果 / 正文），列出最大的单条消息，并找出同一段内容重复出现的地方。

真实审计一个长会话的结果：

```
估算 ≈ 406,525 tokens，675 条消息，19 处重复
  reasoning      156,805  39%   ← 最大的一块，且没有开关
  tool-call      123,754  30%   ← 参数里塞的大段内容也计费
  tool:text      109,958  27%
  assistant:text   8,704   2%
```

两条看起来反直觉、但它如实报出来的结论：

- **推理占 39%**，比工具结果还大。这部分由模型自己产生，压缩不了，只能缩小上下文和任务范围。
- **工具调用参数占 30%**，也就是说"让模型把一大段代码写进参数"和"读回一大段文件"一样贵。

这个工具的边界：

- 数字是**估算**（中文 1 字 ≈ 1 token，英文 4 字符 ≈ 1 token），不是 provider 的真实计数。
- 它**只报告，不改历史**。删掉已提交的事件会破坏 replay / fork / resume，代价远大于省下的 token。
- 它会连带报出**本插件自己**的开销（数据目录里累计多少次强化、产出多少 token），不藏私。

## 输入框左侧的星星

模型选择器左边的工具栏里有一颗星星。

- **点一下**：把输入框里**当前**的草稿送去强化，结果直接回填
- **重新生成**：基于这次的原话再强化一次——不是基于刚生成的那版，所以不会越改越走样
- **还原**：把输入框恢复成这次强化前的原话
- **取消**：强化进行中再点一次星星就中断。按钮会变成红色的 ■ +「取消」，服务端同步停止模型调用，不会出现"界面停了、后台还在烧 token"
- 输入框为空时点，只提示"先写点什么"，不动内容

「重新生成」和「还原」只在这两个按钮对应的结果还留在输入框里时出现。**你一旦动手改输入框，它们就收起来了**——旧结果已经作废，再点星星强化的是你新写的内容，不会回头去强化上一次的提示词。

按钮会跟着状态变：强化中星星呼吸、达标是绿色分数、未达标是黄色分数、失败是红色原因。颜色全部取自主题令牌，所以明暗主题自动跟随；窗口收窄到 560px 以下时收起文字标签和分数，只留星星和两个图形按钮（↻ 重新生成 / ↺ 还原），功能不缩水。

它走的是本机回环路由 `POST /prompt-forge/enhance`，不是把渲染交给浏览器：模型调用和落盘仍然全在 Host 端，并做了同源校验（外来 Origin、带代理头的请求一律 403）和并发上限 2。

### token 角标

星星右边还有一个角标（如 `407k`），显示**当前会话**的估算消耗。点一下在输入框下方展开明细：总量、消息数、按内容类型的占比、重复内容可省多少。

- 角标只在能读到会话时出现；读不到就不显示，不会弹出错误
- 每次展开都重新算一次，数字跟着会话走
- 明细面板占用**输入框下方那一行**（`conversation.composer.dock`），不是浮层——浮层会被输入框的溢出裁切，而那一行本来就分配了空间
- 角标和面板是两个互不相邻的组件，用模块内一个小订阅共享同一份数据
- 数据走 `POST /prompt-forge/audit`，纯计算、不调模型，所以刷新没有成本


## 配置

写在 profile 的 `cordis.patch.yml` 里：

```yaml
- id: prompt-forge
  name: dsh-prompt-forge
  config:
    threshold: 82            # 及格线（0-100）
    maxRepairRounds: 1       # 初评后最多再改几轮（0-3；调 2 更稳但更慢）
    autoLearn: true          # 每 learnEvery 次强化自动挖规则
    autoPromote: false       # 是否连评测也自动跑（费 token，默认关）
    learnEvery: 5
    learnMinOccurrences: 2   # 同一缺陷出现几次才值得写规则
    maxRules: 16
    evalCases: 3             # 一次评测用几条基准用例
    evalVotes: 3             # 评测时每条独立评几次，取多数（1=最快）
    promoteMargin: 2         # 领先多少分才允许晋级（实测噪声约 5，0.5 等于认证噪声）
    noiseFloor: 5            # 领先不到这个数就算晋级，也标记为"可能波动"
    autoRules: true          # 常驻证据规则层（关掉即完全不再注入系统提示）
    benchmarkAuto: true      # 把真实用过的请求自动收进基准集
    benchmarkMax: 12         # 基准集上限（超出先淘汰自动加入的，种子和别人手工加的保留）
    contextEnabled: true     # 用会话最近对话做接地
    planEnabled: true        # 改写前先做一次判断
    contextTurns: 6          # 最多取几轮
    contextChars: 2400       # 接地窗口的字符预算
    provider: deepseek-account   # 留空则跟随会话默认模型
    model: deepseek-flash
    dataDir: /custom/path        # 留空则用 ~/.dsh/prompt-forge
```

`provider`/`model` 必须成对填写；只填一个会被忽略并降级为跟随默认模型。`contextTurns: 0` 或 `contextChars: 0` 等于关掉接地。

## 数据落在哪

默认 `~/.dsh/prompt-forge/`（与本机其他插件的数据目录同级），可用 `dataDir` 覆盖。全是普通 JSON，可以直接看、diff、备份、删：

```
playbook.json     现行策略（版本、评分表权重、规则列表）
state.json        候选版本、计数器、晋级历史
traces.jsonl      每次强化的完整轨迹，一行一条
benchmark.json    评测基准集
versions/vN.json  每个版本的快照（保留最近 keepVersions 个）
```

轨迹文件**不会**被 `reset` 删除——它是学习的证据。

## 设计取舍

- **不 import 任何 harness 包。** 插件通过 `ctx.tools` / `ctx.llm` 的公开方法工作，流式 chunk 自己累加（`lib/llm.js`）。`@deepseek-ai/schemastery` 用受保护的动态 import——能解析就有配置 schema，解析不到就退化为无 schema，**插件永远能加载**。
- **不自动改写你输入框里的字。** 强化是显式调用（工具或你说的那句话），没有偷偷替换。
- **提示词注入防护。** 所有用户文本包在标记块里，且块内出现的同名标记会被转义（`neutralizeTag`），这样原文无法提前闭合自己的块去伪造指令。
- **写盘原子性。** 临时文件 + rename；损坏的 JSON 会被挪到 `.corrupt-<时间戳>` 而不是让插件卡死。

## 已知限制

- 评测会消耗 token：`evalCases × 2 × (1 + 修复轮数) × evalVotes` 次调用。默认 `evalVotes: 3` 就把评测放大三倍——一次评测可能要跑几分钟。`autoPromote` 默认关闭正是为此；日常强化不受影响（`critiqueVotes` 默认 1）。
- 评分质量取决于所用模型。用弱模型当裁判，分数区分度会下降；`self_check` 会在路由不可用时直接报 FAIL。
- 基准集初始是 3 条通用用例，只能防止明显退步；要它真的贴合你的用法，用 `add_case` 加你自己的真实请求。
- 星星按钮依赖插槽 `conversation.composer.dock` 和 `inputActions.setDraft`。宿主若不提供回填能力，按钮会置灰而不是假装成功。
- 同 profile 里的 `dsh-prompt-enhance` 负责输入框内的一键强化和预览面板；本插件管评分闭环、进化，以及模型选择器左边的星星。两者不冲突。
